# Infomart 発注ナビ v1.8.0

個人数量（defaultQty）・発注間隔（intervalMode / intervalDays）・最初の発注日（firstOrderDate）・個人プリセットだけを、Supabase auth.uid() ごとに同期します。クラウド設定のボタンで明示的に保存・取得します。端末編集を自動送信する機能はありません。

発注履歴、取引カレンダーの個人データ、pendingRun、日別数量変更、予定への自動追加ON/OFF、確認状態、ローカル設定は端末保存を維持します。共通商品・発注先同期の処理は維持しています。

## SQL実行手順

1. 既存Supabaseプロジェクトのバックアップを確保し、SQL Editorで `sql/upgrade-v1.8.0-personal.sql` 全文を実行します。既存v1.7.1の基盤セットアップSQLは再実行しません。
2. SQLはトランザクション内でpersonal_settings、本人閲覧RLS、保存RPCだけを追加します。既存organizations / stores / org_members / shared_master / cloud_auditの定義・データは変更しません。同じアップグレードSQLの再実行も可能です。
3. 新規プロジェクトだけは基盤セットアップSQLの後に、このアップグレードSQLも実行します。
4. PR承認・マージ後に通常の配信手順でv1.8.0を配置し、PC/iPadでアプリ版を確認します。本PRの準備では本番DB変更・mainへのマージ・デプロイは実行しません。
5. 接続には既存Project URLとPublishable keyを使用します。Secret/service_roleはブラウザへ入力しません。

## 個人同期と移行

- ログイン後、端末利用者を確認してクラウド設定を開きます。クラウド未登録なら「個人設定を初回アップロード」で一度だけ移行します。端末設定は削除しません。保存済みなら同じボタンは更新になります。
- 新端末は同じクラウドアカウントにログインし、共通マスターのID/codeが揃った状態で「個人設定をクラウドから取得」を明示選択します。初回取得でローカル4項目を置換する前に復元ポイントを保存します。
- 1クラウドアカウントは各端末の1利用者に紐付けます。別アカウントや別会社は別の端末利用者を追加して使用します。別利用者から既存の紐付けを無断で使用できません。
- 版番号不一致では保存を拒否します。端末をバックアップしてからクラウド取得を選択し、必要なローカル編集を再適用して保存します。強制上書き機能はありません。
- 通信後に利用者・アカウント・共通マスター・ローカルデータ・他タブの保存が変わった場合は反映を停止します。送信後に通信が失敗した場合、成功を推測して再送せずクラウド取得で確認します。
- 削除商品は復活しません。商品IDとcode両方を検証し、不明なプリセット参照やクラウド設定は取得・保存を停止します。削除商品を参照するプリセットは元端末で明示的に編集/削除し、最後に取得した版から保存してください。別端末から先に取得できない場合は元端末で整理して再保存します。
- 復元ポイントを保存できない場合は同期を停止します。復元操作は既存の「設定・保守」で行います。

## PC → iPad v1.8.0 E2E確認手順

v1.7.1の共通マスターE2EはPASS済みの前提を維持し、再実施しません。以下は今回追加した個人同期だけの確認です。発注・カート・確定操作は対象外です。

1. PC通常ブラウザでv1.8.0を確認。同じ共通マスターを使用し、ローカルバックアップを保存。商品1件の数量、7日間隔、最初の発注日、プリセット名・数量を記録します。
2. 同期状態と端末利用者名・クラウドメールを確認し「初回アップロード」。保存版と時刻を記録。数量・履歴・カレンダー・pendingRunのローカル内容が消えていないことを確認。
3. iPad Safariでv1.8.0と同じアカウント、共通商品ID/codeを確認。「クラウドから取得」の確認画面で4項目の置換を承認。PCと数量・間隔・日付・プリセットが一致することを記録。iPad自身の履歴・カレンダー・pendingRunが保持されることを確認。
4. iPadで対象4項目を編集してクラウド保存。PCで最新版確認→取得し、iPadの値に一致することを記録。
5. PC / iPadの両方で同じ版を取得してから異なる数量を編集。PCが先に保存した後、iPad保存が競合停止し、iPadのローカル値が保持されることを確認。バックアップ後に取得を選択して解消。
6. PC InPrivateは同じアカウントで初回取得を確認。別アカウントでは他人のpersonal_settingsが見えず、他人への直接PATCH/POSTが拒否されることをData APIで確認（JWTやキーを証跡に残さない）。管理者も他人の個人データを読めないことを確認。
7. テスト用の削除商品参照・不明コード・途中ログアウト・オフラインで成功表示/黙った復活が起きないことを確認。SQL未適用時もローカル4項目が保持されることを確認。
8. 各端末の版、ブラウザ、保存版、期待値/実値、日時、画面証跡を残し、v1.8.0のPASS/HOLDを判定します。v1.7.1の既存Evidenceと区別します。

## ローカル検証

`pnpm install --frozen-lockfile` → `pnpm test` → `pnpm check` → `git diff --check`。

既存13件＋新規15件（計28件）。新規には実SQLをPGliteで実行するDBテストを含みます。Supabaseのauth.uid()はJWTのsubを読むテスト関数で置換し、実際のauthenticated/anonロールとRLSを検証します。pgcrypto拡張のロードだけはローカル環境では省略します。実サービスの認証・ネットワーク・iPad挙動はこのテストでは保証しません。

RLS/RPC設計の参考: https://supabase.com/docs/guides/database/postgres/row-level-security および https://supabase.com/docs/guides/database/functions 。保存RPCはsecurity definerですが、ユーザーIDを引数として受けずauth.uid()から算出し所属会社を毎回確認、search_pathを空に固定、PUBLIC/anonの実行権限を剥奪します。直接DML権限はauthenticatedにもありません。共通マスターを行ロックしてID/codeを検証し、版番号一致時だけ原子的に保存します。
